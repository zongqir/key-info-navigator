# 文档锁定状态监听机制说明

**更新日期**: 2025-10-02  
**版本**: v1.3.0

## 🎯 监听机制概述

插件提供了两种监听文档锁定状态变化的机制：

1. **MutationObserver（事件驱动）** - 默认方式，推荐使用
2. **定时检查（轮询）** - 可选的兜底机制

---

## 📊 两种机制对比

### 1️⃣ MutationObserver（事件驱动）✅ 推荐

**工作原理**：
```typescript
// 监听面包屑区域的属性变化
observer.observe(targetNode, {
    attributes: true,
    attributeFilter: ['aria-label', 'data-subtype', 'xlink:href']
});

// 当这些属性改变时，立即触发回调
observer.callback = (mutations) => {
    if (有锁按钮相关的变化) {
        检查状态并通知订阅者
    }
};
```

**优点**：
- ⚡ **实时响应** - 状态改变立即触发，延迟 < 10ms
- 🎯 **精确监听** - 只监听相关属性，不做无用检查
- 💡 **性能最优** - 不消耗额外的定时器资源
- 🔋 **省电** - 只在有变化时才执行，不持续运行

**缺点**：
- ⚠️ 依赖 DOM 事件 - 如果思源未触发事件，可能漏检
- ⚠️ 复杂场景可能失效 - 某些特殊情况下 DOM 可能不触发 mutation

**使用场景**：
- ✅ 日常使用（推荐）
- ✅ 注重性能和电池续航
- ✅ 锁按钮状态变化都会触发 DOM 更新的情况

---

### 2️⃣ 定时检查（轮询）⏰ 兜底机制

**工作原理**：
```typescript
// 每隔一段时间主动检查一次
setInterval(() => {
    const newState = isCurrentDocumentReadonly();
    if (newState !== lastState) {
        通知订阅者
    }
}, 3000); // 默认每3秒检查一次
```

**优点**：
- 🛡️ **兜底保障** - 即使 MutationObserver 漏检也能发现
- 🔄 **强制同步** - 定期主动检查，不依赖事件
- 🐛 **调试友好** - 更容易发现状态不同步的问题

**缺点**：
- 🐌 **有延迟** - 最多延迟3秒才能检测到变化
- 💻 **消耗资源** - 持续运行定时器，即使没有变化
- 🔋 **耗电** - 每3秒执行一次检查，增加CPU负载
- 📊 **日志噪音** - 频繁检查产生大量调试日志

**使用场景**：
- ⚠️ 发现 MutationObserver 漏检的情况
- ⚠️ 需要绝对保证状态同步
- ⚠️ 调试或测试阶段

## 🚀 如何使用

### 方式1: 纯事件驱动（默认，推荐）

```typescript
import { DocumentReadonlyChecker } from '@/modules/utils';

// 添加监听器，使用默认的纯事件驱动
DocumentReadonlyChecker.addStateChangeListener((isReadonly) => {
    console.log('文档状态变化:', isReadonly ? '🔒 锁定' : '✏️ 解锁');
    // 更新UI...
});

// 日志输出：
// 🔄 [DocumentReadonlyChecker] 开始监听文档状态变化 (纯 MutationObserver)
// 🔄 [DocumentReadonlyChecker] MutationObserver已启动
```

### 方式2: 事件驱动 + 定时兜底

```typescript
import { DocumentReadonlyChecker } from '@/modules/utils';

// 添加监听器，启用定时检查作为兜底
DocumentReadonlyChecker.addStateChangeListener((isReadonly) => {
    console.log('文档状态变化:', isReadonly ? '🔒 锁定' : '✏️ 解锁');
    // 更新UI...
}, true); // 第二个参数设为 true

// 日志输出：
// 🔄 [DocumentReadonlyChecker] 开始监听文档状态变化 (MutationObserver + 定时检查兜底)
// 🔄 [DocumentReadonlyChecker] MutationObserver已启动
// 🔄 [DocumentReadonlyChecker] 定时检查兜底已启动（每3秒）
```

### 查看监听状态

```typescript
const status = DocumentReadonlyChecker.getMonitoringStatus();
console.log('监听状态:', status);

// 输出示例：
// {
//   isMonitoring: true,        // MutationObserver是否运行
//   isPollingEnabled: false,   // 定时检查是否启用
//   listenerCount: 1,          // 订阅者数量
//   currentState: true         // 当前状态（true=锁定）
// }
```

## ⚙️ 配置参数

### 定时检查间隔

当前硬编码为 3000ms（3秒），如需修改：

```typescript
// src/modules/utils/DocumentReadonlyChecker.ts 第154行
this.pollingTimer = window.setInterval(() => {
    this.checkStateChange();
}, 3000); // 修改这里的数值（单位：毫秒）
```

**建议值**：
- 🚀 **1000ms (1秒)** - 快速响应，但消耗较多资源
- ✅ **3000ms (3秒)** - 平衡性能和响应（默认值）
- 🐢 **5000ms (5秒)** - 省电模式，响应较慢

## 📝 常见问题

### Q1: 我应该使用哪种方式？

**A**: 推荐使用**纯事件驱动**（默认方式）

```typescript
// ✅ 推荐：性能最优，适合99%的场景
DocumentReadonlyChecker.addStateChangeListener(callback);

// ⚠️ 仅在以下情况考虑启用定时兜底：
// 1. 发现 MutationObserver 确实漏检了
// 2. 正在调试状态同步问题
// 3. 需要绝对保证状态同步（如金融、医疗等关键应用）
DocumentReadonlyChecker.addStateChangeListener(callback, true);
```

### Q2: 定时检查会影响性能吗？

**A**: 有轻微影响，但不明显

- ⚡ 每3秒执行一次 `isCurrentDocumentReadonly()`
- 📊 查询几个 DOM 属性，耗时 < 1ms
- 🔋 对电池续航有轻微影响（移动设备更明显）
- 📝 会产生额外的调试日志（开启调试模式时）

### Q3: 为什么不直接用定时检查？

**A**: 因为事件驱动有明显优势

| 对比项 | MutationObserver | 定时检查 |
|--------|------------------|----------|
| 响应速度 | ⚡ < 10ms | 🐌 0-3秒 |
| CPU占用 | 💡 仅在变化时 | 💻 持续运行 |
| 电池消耗 | 🔋 最小 | 🔋 中等 |
| 调试日志 | 📝 仅在变化时 | 📝 每3秒一次 |

### Q4: MutationObserver 会漏检吗？

**A**: 理论上可能，但实际很少见

**触发 MutationObserver 的情况**（都能正确检测）：
- ✅ 用户点击锁按钮
- ✅ 使用快捷键切换锁定状态
- ✅ 插件代码调用锁按钮的 click()
- ✅ 思源内部切换文档状态

**不触发 MutationObserver 的情况**（极少见）：
- ⚠️ 直接修改内存中的状态，但不更新 DOM（思源不会这样做）
- ⚠️ 使用非标准方式绕过 DOM 更新（极端情况）

## 🎓 设计理念

### 为什么提供两种模式？

1. **MutationObserver** - 满足 99% 的日常需求
2. **定时检查** - 作为兜底，提供额外的安全保障

### 为什么默认关闭定时检查？

1. 🎯 **性能优先** - 大多数情况下事件驱动已经足够
2. 🔋 **省电** - 移动设备电池续航更重要
3. 📝 **减少噪音** - 避免产生大量调试日志
4. ⚙️ **灵活配置** - 需要时可以轻松开启
